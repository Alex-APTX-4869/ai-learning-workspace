# 课程需求确认 Agent

## 为什么是一个 Agent

用户需要的是一段连续、可理解的需求确认对话，因此界面只呈现一个“需求确认 Agent”。它在主流程中依次使用三种受限职责，并提供一种按需辅助职责，但不采用多个自治 Agent 相互讨论：

1. **需求分析**：根据初始想法生成三档访谈深度，并推荐其中一档。
2. **逐题访谈**：根据此前回答，每次只提出一个最值得确认的问题。
3. **需求归纳**：把最终答案整理成结构化 `CourseBrief`（课程需求档案）。
4. **选项解释**：只在用户主动点击某个选项的“解释”时，结合当前需求说明选项含义、适用情况、课程影响和例子。

这些职责使用会话启动时冻结的模型路由，可以分配不同模型。选项解释会真实调用模型，但它是只读辅助调用，不替用户作答，不写入访谈轮次，也不改变会话状态、题数或版本。状态迁移、题数、稳定 ID、数据校验和课程创建都由 Python 工作流控制，LLM 不能自行改状态或写数据库。

## 用户流程

```text
输入课程想法
      ↓
AI 给出三档深度（标题 + 解释 + 题数 + 推荐）
      ↓
用户选择一档，或输入 1～20 的自定义题数
      ↓
AI 按第一性原理逐题确认
（每题按实际需要决定选项数量，A、B、C… + 用户自由输入）
      ↓
每个新问题恰好标出一个“推荐”并说明依据
（推荐不自动选中，也不表示正确答案）
      ↓
生成结构化课程需求档案
      ↓
用户最终确认（关键歧义在归纳前自动补问，每次题额加一）
      ↓
创建课程，并把需求档案交给大纲与知识点生成
```

“第一性原理”在这里不是泛泛追问，而是从最终可验证的学习成果倒推必要能力、范围与现实约束；区分用户已经确认的事实和仍未确认的假设；每题只消除一个最影响课程设计的未知量。

访谈 Agent 会综合初始描述和全部历史回答中有关学习基础、实践经验、术语熟悉度的证据调整措辞。证据明确时匹配用户当前水平；证据不足时使用小白也能理解的语言，并优先确认基础。无法避免的专业术语会紧接简单解释。

选择 `N` 题后，基础主流程需要一次分析深度、`N` 次动态提问和一次归纳。用户自由回答或题数用尽时，另作歧义评估；关键歧义可以自动补问一次，显示理由并将题额加一，不再等待批准。不是每个回答都额外调用评估。用户明确表示“不知道/尚未收到说明”时，不反复逼问相同外部事实。

解释采用 Markdown 增量输出；同页只缓存完整成功结果。切换问题/选项取消旧解释请求，收起面板不影响当前解释继续生成。失败可保留已显示片段，但不会缓存为完成结果。

## 状态与数据

会话主流程与补问分支：

```text
choosing_depth → interviewing → ready_to_confirm → completed
                       ↓关键歧义
               自动加一题 → interviewing
```

旧 `awaiting_extension` 会话通过兼容恢复入口继续，不是新流程的审批步骤。

- `intake_sessions` 保存初始输入、三档方案、选定题数、当前问题、最终需求档案、课程 ID 和并发版本号。
- `intake_turns` 每题一行保存问题与回答，方便恢复、审计和以后支持修改答案。
- `course_id` 有唯一约束；确认课程是幂等的，重复提交不会创建第二门课程。
- 增量迁移 `20260909_04_intake_extensions` 给会话增加申请和决策历史字段，保留已有回答和课程。
- 不再提供用户手动加题。Agent 判断关键歧义后自动加一，初始题数仍为 1～20，补问可超过初始题额；提示词禁止重复补问，但不是数学上保证终止的硬上限。
- 后端核对会话状态和版本，迟到或重复提交不能重复加题。旧审批端点仅用于兼容恢复。
- 选项解释只在模型返回前后检查当前问题是否仍然有效，不修改 `intake_sessions` 或 `intake_turns`。

`CourseBrief` 当前包含：课程名称、摘要、学习者情况、学习成果、范围内、范围外、学习偏好、现实限制和完成标准。创建课程后，这份档案会成为后续章节、小节和知识点生成的主要上下文；旧课程没有档案时仍回退到原来的名称和简介。若用户后来明确编辑课程名称或简介，最新课程信息优先于旧档案中的冲突内容。

## API

```text
POST /course-intakes
GET  /course-intakes/latest-active
GET  /course-intakes/{id}
POST /course-intakes/{id}/depth
POST /course-intakes/{id}/answers
POST /course-intakes/{id}/questions/{question_id}/options/{option_id}/explain
POST /course-intakes/{id}/questions/{question_id}/options/{option_id}/explain-stream
POST /course-intakes/{id}/extension-decision
POST /course-intakes/{id}/confirm
```

- 创建会话：`{"name": "课程名称", "intro": "目前的想法"}`
- 选择 AI 档位：`{"option_id": "depth_2"}`
- 自定义题数：`{"question_count": 5}`
- 选择答案：`{"question_id": "question_1", "option_id": "option_2"}`
- 自由回答：`{"question_id": "question_1", "custom_answer": "我的实际情况"}`
- 审批补问：`{"expected_version": 8, "proposal_id": "申请 UUID", "approve": true}`。
- 新解释端点无需请求体，返回 NDJSON `delta` / `done` / `error` 事件，增量文本交给安全 Markdown 渲染。旧 `explain` 保留兼容；旧 `extra-question` 返回 410。

## 恢复与旧会话兼容

- 前端在 `localStorage` 保存当前活动会话 ID。关闭弹窗、刷新页面或重新打开创建流程时，先按该 ID 恢复；本地没有有效 ID 时，再请求最近一个未完成会话。
- 用户点击“重新开始”时，会清除活动 ID，并在当前浏览器记录这次被主动跳过的会话，避免它立刻又被 `latest-active` 自动恢复。
- 会话完成后会清除本地恢复标记。数据库始终是访谈内容和状态的事实来源，`localStorage` 只保存恢复入口。
- 已持久化的旧问题 JSON 没有选项推荐和推荐理由。`QuestionOption.recommended` 对旧数据默认 `false`，`InterviewQuestion.recommendation_reason` 默认空字符串，因此旧会话仍能读取并继续回答。
- 新问题至少有两个不同选项，不设五项上限，恰好推荐一个；标题去空白并忽略大小写后不能重复。旧问题和回答缺少 baseline 时按空字符串读取。

## 质量与安全边界

- 三档数量由 Pydantic 强制校验为恰好三档、题数严格递增、恰好一档推荐，题数范围为 1～20。
- 选项数量由 Agent 根据决策需要决定，不固定档位、不凑数；前端完整展示，字母编号超过 Z 后继续 AA，“自己输入”作为独立入口固定提供。测试大数量仅验证渲染不会截断，不表示鼓励生成冗长选项。
- 每个新问题恰好一个选项标记为推荐，并提供通俗的推荐依据。推荐只表示根据当前已知信息更匹配，不会自动选中，也不会覆盖用户最终选择。
- 推荐与选项解释都只依据用户明确提供的信息，不把推测当成事实；界面明确说明解释和推荐不代表正确答案。
- 每个问题有 `focus_key`。后端不接受已使用的关注点，并且只允许一次有限重试，防止重复或无限循环。
- SystemMessage 保存规则，HumanMessage 只承载 JSON 用户资料；模型输出仍必须通过结构校验。
- 模型等待期间不长期持有数据库锁；回写前检查会话版本和当前问题，迟到结果不能覆盖新状态。
- 模型失败不会推进会话或清空页面中的已选答案，用户可以原地重试。
- 右侧选项解释面板由用户按需打开，可随时收起；切换到下一题时自动关闭。解释失败只影响该面板，不阻止用户选择或提交答案。
- 自动测试替换模型调用，不消耗额度；实际页面没有模拟数据，会调用冻结配置的模型 API。

## 后续增强

当前覆盖真实访谈、流式解释、自动补问和活动会话恢复。后续可增加：主动取消、提前结束访谈、返回修改历史答案、需求档案版本及访谈后台任务。访谈与解释仍是请求内调用，不能承诺关闭页面后会自动完成；内容制作与讲师问答使用的持久队列是另一条流程。

## 选项决策一致性（2026-09-15）

正常问题和自动补问共用 `question_policy.py`，同时使用资料范围规则；不增加一个自治审查 Agent 或每题一次额外模型调用。

- 范围/深度：保留已确认的共同基础，只比较额外覆盖的边界；适合递进才递进，不默认越多越好。
- 偏好：在同一范围下比较一个维度的取舍，不把非首选内容自动排除。
- 外部事实：依据明确说明，不从教材出现公式推断不考代码；无证据时提供“不确定”，不能以推荐代替事实。
- 问题的 `baseline` 简述有依据的共同前提，显示在题目下，随普通选择和自由回答保存，最终归纳、选项解释都继承此前需求。该字段是模型摘要，不是新增用户授权；用户明确纠正优先。
- 原有已显示问题不会被静默重写，新规则从下一次模型生成生效；不清空历史答案。

结构检查能验证字段、推荐数和重复标题，不能证明语义互斥或范围继承一定正确。需继续用案例评估真实输出。回归：`python -m unittest backend.tests.test_intake`、`npm run test:intake-question`；真实模型小样本：`python -m scripts.accept_intake_decisions_live --confirm-live`（三次合成需求调用，不修改实际访谈，可能计费）。
